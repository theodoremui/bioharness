### Tools, harnesses and agents {#bg-agents}

A language model on its own can only produce text. **Tool calling** lets that text trigger actions. The model writes a request in an agreed format, for example `pose2d(video)`; surrounding software detects it, runs the named program and pastes the result back into the model's input; the model then continues writing. Toolformer [@schick2023] showed that language models can learn when to call a calculator or a search engine in the middle of a sentence ({fig:toolformer}).

@fig toolformer | figures/papers/toolformer_fig1.png | Tool calls inside text. The model writes a call (colored), the call is executed, and its result (after the arrow) becomes part of the text the model continues from. Reproduced from @{schick2023}, Fig. 1.

The surrounding software is the **harness**. It holds the list of tools and their descriptions, runs the calls, keeps a transcript of everything that has happened, decides what the model is shown (a full array of numbers, a short summary or a plot) and stops the run when the model submits its answer. Harness design matters: SWE-agent [@yang2024] made a language model much better at fixing software bugs largely by redesigning the commands and feedback its harness offered ({fig:swe}).

@fig swe | figures/papers/sweagent_fig1.png | A harness sits between the model and the computer. It defines which commands the model can issue and what feedback comes back. Reproduced from @{yang2024}, Fig. 1.

A model and its harness working together over several steps form an **agent**, and one complete run, from reading the task to submitting the answer, is a **trajectory**. {fig:agent-loop} shows the agent studied here. Besides the video and the task text, the harness passes the person's height and the phone's lens parameters to the tools that need them. Its tools are standard computer-vision programs: a frame viewer that returns chosen frames, optionally cropped; a 2D pose detector, RTMPose [@jiang2023], which marks the joints in every frame; a segmenter, SAM 2 [@ravi2024], which outlines the person; a point tracker, CoTracker3 [@karaev2024], which follows chosen points through the video; OpenCap Monocular for 3D joint angles and the center of mass; a plotter; and a Python sandbox, a protected space where short programs written by the model can run on the tool outputs.

@fig agent-loop | figures/fig_agent_loop.svg | The agent. (A) The model writes tool calls, the harness runs them and returns the results, and the final submission passes through the fixed StaBLE formula. (B) An illustrative trajectory for rise to toes.

The agent route divides the work according to what each part does well. Established tools, several of them validated against laboratory motion capture on common movements, handle geometry, so the model never has to estimate a speed from pixels, which is where the pilot's untrained models failed. The model handles the steps that call for flexible decisions expressed in language and code: reading the task description, choosing tools that suit it, using a plot to locate when the rise began, flagging a tool output that looks implausible and trying another tool, and writing the few lines of code that turn a center-of-mass curve into a peak speed. (The curve lists the height of the center of mass in every frame. If the height rises by 0.005 m between two frames 1/60 s apart, the upward speed there is 0.005 ÷ (1/60) = 0.30 m/s; the code repeats this for every pair of frames in the rise and keeps the largest value.) Because the score comes from features through a fixed formula, every score traces back to the code and tool outputs that produced it, which a clinician can inspect; whether that code measures the intended feature still has to be tested. Two recent results support this division: a code-writing biomechanics agent answered timing questions better when given a validated gait-event tool [@cotton2026], and reinforcement learning taught a VLM when and where to zoom into an image [@zheng2025].
